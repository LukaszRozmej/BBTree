BBTree review benchmark, 2026-10-26
Baseline: 88f88f1a92c3733b8c79c060a479af1efccb095a
Candidate: the changes accompanying this report (exception recovery and empty-leaf compaction).
Windows x64; AMD Ryzen 7 5800X; .NET 10.0.9; AVX2; workstation GC.

Method: separate processes, baseline and candidate run sequentially; five samples per cell.
The ordinary harness warms each cell. Churn uses three complete warmup passes before five measured passes.
The same churn harness was copied into the baseline worktree. No tests or other benchmarks ran alongside these measurements.
These are local measurements, not statistical confidence intervals. Background machine activity was not controlled.

Commands (run in both worktrees after a Release build):
dotnet run --no-build -c Release --project bench/BBTreeBench -- --key u64,str-json --size 10k --map bbtree,bbtree-concurrent --op random_insert,get_hit,range64,random_remove --reps 5
dotnet run --no-build -c Release --project bench/BBTreeBench -- --churn --reps 5

Churn: 100 batches, a 10,000-key live window, 2,000,000 timed insert/remove operations.
Median: 49.6 -> 46.6 ns/op (6.0% lower in this run).
Allocated during churn: 16,600,288 -> 20,170,152 bytes (21.5% higher).
Median retained managed memory with 10,000 live keys: 16,721,824 -> 172,272 bytes (99.0% lower).
Median retained after draining: 16,770,976 -> 4,840 bytes (99.97% lower).
Retained memory is the delta of GC.GetTotalMemory(true) while keeping the map alive; runtime noise is included.

Interpretation: compaction bounds retention under moving-key churn and reuses surviving leaves.
It adds routing/list allocations and occasionally locks the tree. Concurrent removal medians rose about 4-5% in the 10k cells.
Read and scan timings are close enough to the observed run variation that no general speedup is claimed.
These measurements do not quantify compaction tail latency, throughput with contending writers, or other key types.
